# 从报告修订中吸收经验

> 标题以用户选择的 `assets/templates/early.json` 或 `mid-late.json` 为唯一来源。本文件的旧例仅说明标题内部的内容写法，不能用于选阶段、改题、裁剪、合并或新增章节。先执行 [阶段模板规则](stage-template-workflow.md)。

当用户要求按修订、批注或截图改稿，或把修改经验更新到本技能时，先逐项对照，再提炼规则。此文件记录写作方法，不存放真实项目的姓名、金额、交易和未公开问题。

## 修订处理

1. 同时读取接受修订前后文本、插入与删除、格式变化、批注及其锚点、正文中的编辑留言。截图用于确认反馈位置和意图；无独立评论节点不等于没有修改意见。
2. 把反馈分为保留插入、执行删除、措辞简化、整段重写、数字/口径调整、结构与格式六类，逐项记录处置。纯格式修订同样检查，不只提取可见正文。
3. 整段删除不代表其中所有事实失实；按用户要求删去，不在后文换句话补回。明确要求“重写”时，从原始段落或已提供资料中提取所需事实重组，不能接受删除后留下空标题。
4. 修改意见本身不进入成稿。原文件另存保留；默认交付已接受原修订并落实反馈的清稿，用户要求保留修订时提供可审阅的修订稿。清除空白表格、残留空段及无效批注锚点，核对编号与分页。
5. 数字冲突、证据不足和未完成核验保持边界。改口吻不代表重新尽调，不用“已核实”“审计确认”等提高证据等级。

## 可复用反馈与处理

| 修改意图 | 技能应采取的行为 |
|---|---|
| 报告像第三方在指导我们 | 采用本方项目团队汇报视角，说明事实、判断及必要后续工作 |
| 把“应核查”删去或改成“将在尽调阶段” | 先完成现有材料支持的分析；确需保留行动时使用本方计划，不批量换词保留任务堆叠 |
| 将“股东表列示”“回复花名册人数”简化 | 正文直接陈述公司事实，表头写业务字段，文件名留在台账 |
| 删除频繁的“在尽调中回复” | 同段或同表交代一次必要归属；口头信息、解释和预测仍保留边界 |
| 删除资料版本号与磋商流水 | 正文采用有效方案，融资交代金额、估值、用途；重要变更按业务事实说明 |
| 删除大段表格后的复述和重复核查 | 表格承担可比数据，正文解释关系和影响；不固定设置判断加核查的结尾 |
| 删除任职冲突、人员调整流水及无关关联企业长表 | 保留当前关键职务、人员构成和项目相关主体；未解实质差异在交付说明提示，琐碎过程留底稿 |
| 删除专利名称单字差异、尾差说明 | 保留名称、权属与状态，底稿记录校对；表注只解释影响理解的口径，不占用正文讲制作过程 |
| 要求财务问题“数据加结论” | 算清合同、收入、回款、价差等关系，指出证据支持的实际影响；不列一串待执行事项 |
| 要求订单“直接分开考察” | 真正拆分已签、意向、当期收入及交付年度，完成可比分析；不把分类动作写成给团队的建议 |

单个项目中的删改反映该处的取舍，不据此一概禁止风险、表格、来源或必要核查。优先修正产生问题的旧规则和示例，避免只在文件末尾叠加相反指令。将经验写入语言规则、结构说明及适用的检查脚本，并用虚构资料验证；不得上传客户报告或未脱敏修订记录。
