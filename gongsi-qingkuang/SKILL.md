# 立项报告 · 公司情况章节生成技能

## 首先询问阶段，再使用固定模板

**每次为新项目调用本技能，首先询问：“这次项目采用早前期（伊隆纬特）还是中后期（因诺科技）模板？”等待用户回答后再起草。** 用户已在本轮当前项目明确回答的，直接复用答案；三个技能共用同一阶段。不得用融资轮次、规模或业务数量自动推断。安装维护和纯格式修复不触发选模板询问。

用户选择后必读 [阶段模板执行规则](references/stage-template-workflow.md)，只加载对应的 [早前期标题模板](references/template-early.md) 或 [中后期标题模板](references/template-mid-late.md)，实际骨架位于 `assets/templates/early.json`、`assets/templates/mid-late.json`。**普通标题、层级、顺序固定；仅填写已定义的个案变量和重复组。** 根据当前公司资料包逐标题撰写，原案例事实不移植。缺资料先列缺口，不编造、不交付空节。

先用 `python scripts/stage_template.py init --stage early --output 任务目录/draft.json` 生成工作骨架（中后期改为 `mid-late`）；完成标题变量绑定和正文后必须运行 `python scripts/stage_template.py check 任务目录/content.json`。固定模板优先于下文及旧参考中的示例结构；复核时修订正文论证，不自行改题。详细填空、跨Agent降级核对与明确改模板的处理见执行规则。

## 调用与跨 Agent 运行

本技能采用标准 `SKILL.md`（`name` / `description`）入口，支持自然语言匹配或在宿主技能列表中显式选择。安装、迁移或触发异常时读取 [跨 Agent 安装与调用](references/agent-compatibility.md)，按实际产品版本安装完整目录或ZIP并完成调用验收。

执行时以当前已加载 `SKILL.md` 的位置作为技能根目录，先确认所需参考文件及脚本可读；文内 `scripts/`、`references/`、`assets/` 都相对此根目录解析，不相对用户任务目录。下文的 `python scripts/...` 示例需在技能根目录运行，或改为脚本和输入输出的绝对路径；输出文件放用户任务目录。网页检索、文件读取和代码执行使用宿主当前可用的等价工具，不要求特定工具名称。Word需要Python 3.10+及 `requirements.txt`；无执行或字体条件时如实说明能力边界。

## 公文格式硬规则

以下规则用于生成、改稿和格式检查；旧范文中的格式以本节为准：

1. **括注**：成对中文圆括号 `（…）`、英文圆括号 `(...)` 及其中中文统一楷体_GB2312、三号（16pt），包括括号本身及嵌套括号。适用于标题、正文、表注、附件和落款；未配对括号不改变后续文字格式。
2. **表格优先使用五号**：所有单元格（含表头）固定五号（10.5pt）；中文默认仿宋_GB2312，圆括号及其中中文改为五号楷体_GB2312。括注不能把表内文字放大成三号。表头加粗、浅蓝底、跨页重复，单元格水平及垂直居中，表宽随窗口调整。
3. **四级标题**：按所选模板使用 `（1）标题`，三号仿宋_GB2312、加粗、首行缩进2字符。编号 `（1）` 按标题规则处理；标题中另外出现的解释性括注仍用三号楷体_GB2312并保留加粗。正文默认不加粗。
4. **最后统一西文字体**：先设置方正小标宋简体、黑体、楷体_GB2312、仿宋_GB2312及页脚宋体，再对全文所有西文字体槽 `ascii/hAnsi/cs` 统一设置 Times New Roman。覆盖封面、各级标题、正文、括注、表格、表注、附件、页眉页脚和域显示结果；数字、英文字母、百分号 `%`、西文标点及短横线均适用。保留 `eastAsia` 中文字体、字号和加粗，清除西文主题字体覆盖，不能把中文字体也改为 Times New Roman。
5. **页脚**：页码采用 `-1-` 格式（随后为 `-2-`、`-3-`），无空格，使用 PAGE 域。两个短横线、页码域及其显示数字全部四号（14pt）；先设宋体，最后按上一条统一西文字体，中文字体槽仍为宋体。启用奇偶页不同（`evenAndOddHeaders`），奇数页右侧、偶数页左侧。
6. **行距和附件**：封面主标题及副标题/部门标题固定30磅，正文和正文内编号标题固定28磅；表格和表注保留专用行距。多份附件用 `附件1.实施方案（试行）`，单份用 `附件：实施方案（试行）`；名称不加书名号或末尾标点，保留固有闭括号。只列实际存在且需要交付的附件。

统一使用 `scripts/build_docx.py`；附件从 `content.json` 顶层 `attachments` 列表传入。表外表注默认仿宋五号，其中括注按第1条为三号楷体。Markdown只表达层级与加粗，字体要求在Word生成和检查时落实。

## 写作立场与成稿逻辑复核

以本机构项目团队成员的立场代用户撰写，供领导及投委会作立项判断。正式书面公文、中性表述，结论力度与证据相称；直接陈述必要性、作用和依据，不用“不是……而是”等否定后肯定的绕行句式，不用夸张宣传，也不在每处优势后机械附加保守判断。

正文禁止“需要后续进行判断”“仍需进一步验证”“有待核实”“后续我们将进一步分析”等拖延判断的套话及同义变体。写完已知事实、因果关系和当前可得结论即可结束段落。真实限制、实质矛盾、预测假设仍直接说明；不能靠删去风险或把公司自述改成事实来制造确定性。必要补证动作只放正文外的资料缺口清单，无实质缺口不凑清单。

**全文完成后、交付前必须读取并执行 [投资逻辑复核](references/investment-logic-review.md)**：按本章职责检查“为什么选择这个赛道、技术强在哪里、公司为何具备实现能力、竞争者追赶的难点和壁垒高度”，将术语与指标翻译成领导能理解的客户价值和投资含义。发现论证断裂时直接补充或修订正文、证据与衔接；固定标题、层级和顺序按用户所选阶段模板保持，个案变量按实际证据填写。不得因逻辑复核自行修改、合并、重排或新增标题。单独写某章时只复核所获材料范围，不虚构其他章节或声称已完成整份报告复核。

先完成逻辑修订，再运行 `scripts/style_check.py` 扫描套话与语言红线并复读全文；Word生成后复核字体及页码。机械扫描不能代替投资逻辑审阅。

本技能只做一件事：把尽调资料包、会议纪要与全网权威检索炼成立项报告的"**四、公司情况**"章节，供投委会回答一个问题——**这家公司的主体、股权、团队、资源与合规状况，是否构成一笔可以推进的投资的基础条件**。写作者是本机构项目团队成员，向内部投委会汇报；以资深一级市场投资经理的判断能力组织材料：客观、公允、中性，事实优先，优势与瑕疵同台，绝不为促成立项而美化，也不因局部瑕疵而无依据否定。骨架与必要表格参照两篇内部范文，正文按事实关系自然行文（伊隆纬特＝早期公司写法，因诺科技＝成长期公司写法）。

成品是双件套：**章节正文**（证据陈列，可直接并入立项报告）＋**待补充资料及后续核查事项清单**（随稿在对话回复中交付，任何情况下不写入报告正文/.docx；用户明确要求时才另存为独立文件）。事实台账保留完整来源；正文选择影响立项判断的事实，实质性缺口进入核查清单。用户已删除的内容不因“事实守恒”而自动补回。无关细节、重复信息及无实质影响的材料差异留在工作底稿，不必逐一转成对外交付项。三源（资料包、会议纪要、联网权威检索）都拿不到的数据，正文与表格一律不写、不留"相关资料尚未提供"类占位语（表格中确实无法删除的单元格填"—"），缺口直接进清单。表格用于可比较的多项数据；正文解释关系、变化和影响，不逐行复述表格，也不将连续叙述强行改成表格。判断必须有事实依据。

## 工作方式

新写章节按下列流程收料、核验、起草。修订已有报告时，先按 `references/review-feedback.md` 逐项对照原文、修订结果及批注，再改受影响内容并复核关联数字；不将单纯改稿扩展为新一轮全量尽调。

## 新写章节执行顺序

1. **收料建台账。** 通读资料包全部文件与会议纪要，按 `references/structure.md` 第 0 节把主体、股东与历次股权变动、团队履历、人员结构、知识产权、资质荣誉、客户供应商、子公司、融资估值、财务数据、合规事项逐条登记进公司事实台账并标注来源文件；会议纪要按第 0.2 节的挖掘清单逐条榨取，每条"公司说法"分类为"可书面验证（转成核查任务）"或"仅口头（挂口径照录）"。资料严重不足时先列缺失清单反馈用户，禁止边写边编。
2. **联网补缺与背景增强。** 资料未覆盖的客观工商与公开信息用 WebSearch / WebFetch 检索权威来源补全；随后跑 `references/data-and-tables.md` 第四节的三大必检——机构股东逐个识别背景（管理人、资金性质），主要客户供应商识别性质（央国企/上市公司/贸易商），官方规则与公开风险核验。公开信息与资料包存在实质冲突时说明差异；已证实的时点更新不并列当成矛盾。
3. **先算后核。** 持股比例、穿透比例、投后估值、稀释、人员占比、收入 CAGR 等先按 `references/data-and-tables.md` 的公式算清并完成数字勾稽（股权合计＝100%、注册资本＝Σ认缴、每次变动后股权表自洽、融资表与股东表交叉验证）；再跑 `references/structure.md` 第 0.5 节的三角验证矩阵（履历↔客户供应商、代持↔核心团队、参保数↔员工数、会议纪要↔书面文件等十四对事实级互锁）。发现矛盾先排查时点、单位和更新关系；未解决的实质差异如实呈现其影响，具体核查步骤归入清单，禁止凑数。
4. **按骨架逐节起草。** 按用户选定的 `assets/templates/` 标题逐项填入事实，`references/structure.md` 仅用于每类内容的"写什么/为什么/怎么写"，配合 `references/writing-craft.md` 的语言红线与句式落笔，表格按 `references/data-and-tables.md` 的模板 T1–T15 生成，随时回看 `references/gold-examples.md` 的范文拆解模仿手法。
5. **红旗扫描。** 每写完一节对照 `references/red-flags.md` 该节的红旗清单逐条扫描；命中事项先写已知事实及其影响；必要核查动作放入清单，正文说明其对当前判断的实际影响；未命中的不写"无"。多面红旗指向同一方向时按第十二节组合拳规则处理。
6. **语言红线扫描。** 逐句过 `references/writing-craft.md` 第〇节的三张清单：禁用连词族（不是……而是等否定-肯定对照句式）零命中、称谓合规（全文零"标的公司"，只用"公司"与简称）、AI 腔与营销腔零命中，且每段首句点明该段核心。命中一处即改写该句。
7. **机械勾稽自检。** 把正文与表格整理成 `scripts/build_docx.py` 用的 JSON 结构，运行 `python scripts/reconcile_check.py content.json` 核验算术（股权求和、人员分项、客户合计、资产负债恒等式、毛利率反算等）；FAIL 项逐条回到原始资料核实，禁止反向改数让脚本通过。再运行 `python scripts/style_check.py content.json` 机械扫描语言红线（称谓/对举连词/结论标签/缺口占位语/外部指导口吻/材料版本痕迹/机械来源句），命中即改写重扫。随后按 `references/writing-craft.md` 末节的成稿质检清单逐项核对。
8. **成稿逻辑复核。** 执行 [投资逻辑复核](references/investment-logic-review.md)，解释团队、权属与组织资源如何支持公司技术和经营能力，保持固定标题、层级和顺序，修订正文证据与因果解释，复跑受影响的数字及语言检查。
9. **交付。** 默认交付 Markdown 正文＋待核查清单，清单在对话回复中输出、不并入正文文件；用户要 Word 时用第 7 步的 JSON 调用 `scripts/build_docx.py` 渲染 `.docx`（见末节），清单仍留在对话中。

## 固定标题模板

早前期：伊隆纬特原第四章“公司情况”，含基本信息、股权变动情况、财务数据，完整30个源标题。中后期：因诺原第二章“公司情况介绍”及第五章“拟投资主体相关情况”，完整95个源标题，保持两个源章节及各自编号；独立的第六章财务分析不默认并入。

完整模板见 `references/template-early.md` 与 `references/template-mid-late.md`；其中人名、股东、历史事项按当前项目实际数量展开。中后期也须逐项填写历史沿革，不能以“成长期”自动压缩成汇总表。资料缺失不得成为静默删节的理由，按阶段模板执行规则处理。

## 语言红线（写作与自检的第一优先级）

三条铁规，命中一处即返工，全文零容忍（细则与改写对照表见 `references/writing-craft.md` 第〇节）：

1. **禁用否定-肯定对照连词族。** "不是……而是""并非……而是""不仅……而是""不止……而是""不仅……而且""不但……还""不只是……更是""与其说……不如说"全部禁止——这类句式绕圈子，一语点不明核心。改法：删掉否定半句，直接写肯定半句；确需对照时拆成两个事实句，用"但""仍""而"承接（范文转折只用"但"："毛利率……提升至42.03%，但2026年一季度回落至23.90%"）。
2. **研究对象的称谓：公司 / 简称。** 全文禁止"标的公司""标的企业""该标的""本标的""目标公司""拟投资标的""标的方"。默认主语用"公司"（范文："公司目前拥有专利17项""公司现有14家子公司"）；财务分析段句首、跨节引用、与其他公司并提处直接用简称（范文："伊隆纬特2023年、2024年和2025年营业收入分别为……"）。简称在章内首次出现全称处括注定义，全章唯一。本方工作用“我们”或“项目组”，与被研究公司区分。
3. **结论先行，一语点明核心。** 每段首句给出该段核心事实或判断，其后才是支撑数据；禁止"随着……的发展"式铺垫开头，禁止"值得注意的是"式引子。

## 必须内化的写作准则

- **五重视角同时在线。** 投资经理（这条信息影响立项判断吗）、尽调（这里藏着什么核查点）、投委会汇报（委员三十秒能看懂吗）、风险识别（缺口与瑕疵在哪）、客观公允（这句话有依据吗）——每段写完用五问过一遍。
- **团队立场与自然行文。** 正文直接汇报事实、关系及判断。段落不套固定“四拍”，判断有事实支撑即可，不强制以核查句收尾。财务问题先把数据和结论写清；必要补证工作放入正文外清单，正文直接给出当前证据支持的判断。
- **表文分工。** 股东、人员、专利和客户明细适合表格；创办背景、团队分工、资金用途及经营变化适合连贯叙述。表后解释集中度、关联关系、差异或影响，不依次把各行念一遍。
- **瑕疵白描＋核查出口。** 0元转让、代持、参保差异、专利受让、子公司真实用途、持续亏损、毛利率波动，照实写入表格与正文，写明证据支持的影响；具体核查动作进入正文外清单，不给每项事实机械追加任务。不回避、不渲染、不定罪。
- **一切有据，缺则查，查不到则进清单。** 资料包 > 联网权威来源 > 写入对话交付的待核查清单（正文与表格不写"相关资料尚未提供"类占位句），三档之外禁止生成任何股东、比例、金额、日期、专利、客户或合规结论。资料包内部各文件冲突（BP vs 简历、访谈 vs 审计报告）与"资料包 vs 公开信息"同规则：先核对是否为真实矛盾、不同口径或已确认更新；实质未解矛盾不隐去，排查过程留底稿。
- **口径三分法。** 审计报告口径、访谈/公司表示口径、本方判断口径永不混写；公司解释及预测保留归属，可在同段起首统一说明；本方判断独立写明依据及边界。不得为减少来源句，将口头说法写成已验证事实。
- **守住章节边界。** 本章只放核心财务快照、问题提示与公司自报预测；深度财务分析归财务章节，产品与商业模式归主营业务分析，市场与政策归行业分析；客户供应商在本章只谈集中度与依赖度。

## Word 输出

渲染前先运行 `python scripts/ensure_fonts.py`：本技能 `assets/fonts/` 自带三款公文字体（仿宋 simfang、方正小标宋简体、楷体_GB2312），缺失时自动做用户级安装（Windows 含注册表注册，无需管理员权限）。生成的 `.docx` 会自动嵌入随附的仿宋_GB2312、楷体_GB2312（方正小标宋许可禁止嵌入，自动跳过），未装这两款字体的机器打开也不掉字；嵌入经反混淆校验，失败时保留未嵌入版本、不影响生成。可用 `python scripts/embed_fonts.py --docx 输出.docx --verify` 复核。

新建章节使用 `scripts/build_docx.py` 排版（三技能共用渲染脚本）。修订用户已有Word时保留原有样式、表格及分页，用文档工具处理修订并渲染检查，无需重建整份文件。新建时把内容组织成 JSON 再运行：

```bash
python scripts/build_docx.py content.json output.docx
```

`content.json` 结构（阶段骨架须由 `scripts/stage_template.py init` 生成；`assets/content_skeleton.json` 为停用入口提示）。封面与目录默认关闭——本章节通常并入整份立项报告；用户要求独立成文时才加 `cover`、把 `toc` 设 true：

```json
{
  "toc": false,
  "blocks": [
    {"type": "h1", "text": "四、公司情况"},
    {"type": "h2", "text": "（一）基本信息"},
    {"type": "h3", "text": "1.工商信息"},
    {"type": "table", "header": ["项目", "内容"], "rows": [["企业名称", "……"]]},
    {"type": "p", "text": "在公司基本情况方面，……"},
    {"type": "tnote", "text": "单位：万元", "align": "right"}
  ]
}
```

缺口数据不进 content.json——正文、表格、note 块都不放"待核查"占位内容，全部缺口在对话交付的待核查清单中提示（见"总体执行顺序"第 8 步）。

块类型：`h1/h2/h3/h4`（标题，编号自带；四级仿宋三号加粗）、`p`（段落，`bold:true` 为核心结论段）、`bullet`（荣誉资质列表）、`table`（`header`+`rows`，宽表给 `widths`）、`tnote`（表注："单位：万元""注：……"，仿宋五号，单位行 `"align":"right"` 放表格上方）、`pagebreak`。表格统一五号（10.5pt），中文仿宋_GB2312、括注中文楷体_GB2312、西文Times New Roman；表头行（`header` 字段即第一行标题）浅蓝底 #D9E2F3 且加粗、跨页重复、宽度按窗口自动调整（占满页面内容区并随页宽缩放）、所有单元格内容水平与垂直居中；表格第一行标题务必放 `header` 字段以获得加粗。正文公文格式（仿宋三号、首行缩进、固定行距 28 磅），页边距上 3.7cm/下 3.5cm/左 2.8cm/右 2.6cm，页脚页码"-1-"格式——以上与 hangye-fenxi、zhuying-yewu-fenxi 完全一致。

## 勾稽机械校验

`scripts/reconcile_check.py` 只做算术核验，作为第 7 步的辅助工具：

```bash
python scripts/reconcile_check.py content.json
```

自动识别股东结构表、人员结构表、客户/供应商表、核心财务表并核验：持股比例求和＝100%、认缴/实缴与工商信息交叉一致、人员分项之和＝总数、客户供应商明细之和＝合计行、资产＝负债＋所有者权益、毛利率反算一致等。数据为空或缺表时标记"跳过"；FAIL 项回原始资料核实数字本身，禁止反向调整。脚本只保证"表格算得对"，红旗扫描、三角验证与语言红线仍需人工逐条跑。

## 读取 .docx 资料包

```bash
python scripts/extract_docx.py "某公司-尽调资料.docx" out.txt
```

逐块输出段落（含样式名）与表格（标 rows/cols），便于建台账。PDF、Excel 资料用对应技能（pdf / xlsx）读取后同样登记进台账。

注意：`build_docx.py` 与 `extract_docx.py` 依赖 python-docx；若默认 `python` 指向缺该库的解释器（如精简 venv），改用装有 python-docx 的解释器运行（通过当前宿主的解释器路径和 `python -m pip show python-docx` 检查）。`reconcile_check.py` 仅用标准库，任何解释器可跑。
