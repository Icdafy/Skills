# 立项报告 · 公司情况章节生成技能

本技能只做一件事并把它做到极致：把项目资料包炼化成立项报告中的"**四、公司情况**"章节。它不是企业宣传册、不是尽调底稿、不是工商信息摘抄，而是投委会用来回答一个问题的证据链——**这家公司的主体、股权、团队、资源与合规状况，是否构成一笔可以推进的投资的基础条件**。默认以一位四十年经验的一级市场股权投资资深业务经理的视角写作：客观、公允、审慎，事实优先，优势与瑕疵同台，绝不为促成立项而美化，也不因局部瑕疵而无依据否定。

## 一句话定位

本章的实质是**用文档形态完成立项阶段的初步尽调**。成品是一份双件套：**证据陈列**——把"这家公司是谁、从哪里来、归谁控制、靠谁经营、凭什么经营"结构化地摆给投委会；**尽调任务清单**——把每一个信息缺口与瑕疵转化为可执行的核查动作，与正文同为正式交付物。资料包里的每个事实只有两个合法去向：进入正文/表格（可溯源），或进入待核查清单（可执行）——不允许第三种去向"悄悄消失"（事实守恒）。写不出意义的事实压缩成表格，给不出事实的判断一律删除。

## 总体执行顺序（不得跳步）

1. **确认资料包到位。** 写作入口是用户提供的企业/项目资料包（BP、工商资料、股权表、章程、团队介绍、花名册、专利证书、审计报告、投资协议、访谈纪要等，一种或多种）。资料严重不足时先列缺失清单反馈用户，不能边写边编。
2. **深度研读 + 建公司事实台账。** 动笔前通读全部资料，按 `references/structure.md` 第 0 节把主体信息、股东与历次股权变动、团队履历、人员结构、知识产权、资质荣誉、客户供应商、子公司、融资估值、财务数据、合规事项逐条登记进台账并标注来源。正文中每个名称、日期、金额、比例都必须能追溯到台账。
3. **补缺：先查资料、再联网。** 资料包未覆盖的客观工商与公开信息（注册资本、股东、变更记录、诉讼、行政处罚、经营异常等），用 WebSearch / WebFetch 检索权威来源（国家企业信用信息公示系统、企查查/天眼查、裁判文书网、执行信息公开网、专利与商标数据库等）补全并登记台账。公开信息与资料包冲突时，两个口径并列呈现并标注"需进一步核实"，**不得替用户作最终判断**。任何数据不得凭空创造；查不到的写"相关资料尚未提供"或"该事项仍需进一步核查"。**资料包内部各文件之间的冲突（BP vs 简历、访谈纪要 vs 审计报告等）按同一规则处理，不得因某份文件更新或更详细就默认采信而略去另一方**，详见 `references/structure.md` 第 0 节。
4. **先算后核再写。** 持股比例、穿透比例、实缴比例、投后估值、稀释比例、人员占比、收入 CAGR 等先按 `references/data-and-tables.md` 算清并完成数字勾稽（股权合计=100%、注册资本=Σ认缴、每次变动后股权表自洽、融资表与股东表交叉验证）；随后跑完 `references/structure.md` 第 0.5 节的**三角验证矩阵**——履历↔客户供应商、代持↔核心团队、参保数↔员工数、融资表↔股东表等事实级互锁，两条各自正常的信息对到一起才暴露问题。发现矛盾的，两处各自如实记录并标注"需进一步核实"，不要边写边凑数，更不要替资料圆谎。
5. **按骨架逐节起草完整正文与表格。** 严格遵循 `references/structure.md` 的标题骨架与每一层"写什么/为什么/怎么写"，配合 `references/writing-craft.md` 的句式与中立措辞落笔，表格按 `references/data-and-tables.md` 的标准模板生成。需要时随时回看 `references/gold-examples.md` 的两份范例标注进行模仿。
6. **红旗扫描与缺口清单。** 每个模块写完即对照 `references/red-flags.md` 该节的红旗清单逐条扫描（代持、0元/低价转让、突击入股、瑕疵出资、参保差异、专利受让、关联交易、对赌回购等四十年见过的死法）；命中的红旗按"现象白描＋核查出口"写入正文或风险表，未命中的不写"无"；未覆盖的信息进"待补充资料及后续核查事项"清单，随成稿一并交付。
7. **成稿自检。** 先把正文与表格整理成 `scripts/build_docx.py` 用的 JSON 结构（即便本轮不出 Word 也整理，因为下一步要用），运行 `python scripts/reconcile_check.py content.json` 做一次机械勾稽核验（股权比例求和、认缴/实缴与工商信息交叉、人员结构分项之和、客户供应商合计、资产负债恒等式、毛利率反算等）；脚本只管算术对不对，不管措辞和逻辑，报出的 FAIL 项逐条回到原始资料核实，不得为了让脚本通过而反向修改数字。算术核验通过后，再按 `references/writing-craft.md` 末尾的质检清单逐项核对：事实可追溯、口径完整、措辞审慎、无宣传语、无机械来源句、表前有引导句、关键表后有分析句、不与主营业务/行业/财务分析章节重复。
8. **按需出 Word。** 默认先交付 Markdown 供审阅；用户要 Word 时，用第 7 步已整理好的 JSON 调用 `scripts/build_docx.py` 渲染为 `.docx`（见末节）。

## 公司情况的标准骨架

骨架抽象自两份范例成稿（早期卫星通信天线公司、成长期工业无人机公司），并补充合规与综合判断两个标准节。编号层级固定为 `四、` / `（一）` / `1.` / `（1）` / `1）`，由调用方写入文本；章序号"四、"随整份报告结构调整，独立交付时保留。条件节不启用时后续编号顺延。

```
四、公司情况                                  ← 章标题（H1）
（一）基本信息                                ← 一级子标题（H2）
   1.工商信息                                 ← 工商信息表 + 主体定位段
   2.历史沿革                                 ← 条件节：业务层面重大节点；股权类变动一律放（二）
   3.核心团队                                 ← （1）（2）…逐人：姓名+职务标题，履历段
   4.人员及组织架构                           ← 专业/学历/年龄结构表 + 组织模式段
   5.知识产权                                 ← 总量分项 + 权属来源 + 明细表
   6.荣誉及资质                               ← 条件节：按国家级/省级/市级/资质认证分组
   7.关联公司（子公司及对外投资）             ← 条件节：子公司表 + 主体清晰度分析
   8.前五大客户及供应商                       ← 分年度客户表、供应商表 + 集中度分析
（二）股权变动情况
   1.股东结构                                 ← 当前股东表 + 股东身份识别段 + 穿透表（含代持披露）
   2.历史股权变动                             ← 初始股权表 + 逐次变动（1）（2）…每次附变动后股权表
   3.历史融资及估值情况                       ← 融资历史汇总表（时间/投资方/投资额/投后估值/轮次）
（三）财务数据
   1.核心财务数据                             ← 资产负债/利润/现金流三段式核心表 + 趋势分析段
   2.存在问题（及对策）                       ← 逐项：事实数字 + 归因 + 待验证判断（+公司对策）
   3.财务预测                                 ← 公司自报口径预测表，注明"公司根据在手订单预测"
（四）合规、信用及重大风险事项                ← 风险核查表 + 已核查范围说明 + 待核查事项
（五）上市规划                                ← 条件节：时间表 + 上市标准表 + 差距分析
（六）公司情况综合判断                        ← 事实基础 + 投资判断 + 待核查事项，绝非宣传总结
```

结构自适应：按资料完整度与公司阶段裁剪。早期公司（如范例一）通常无荣誉资质、无子公司、无上市规划；成长期公司（如范例二）人员结构可简写、股权变动可只保留融资汇总表。裁剪规则详见 `references/structure.md` 末节。（四）（六）两节为本技能标准配置；若用户机构模板明确不含，可将合规要点并入财务"存在问题"、删去综合判断。

## 必须内化的写作准则

- **五重视角同时在线。** 投资经理视角（这条信息对立项重要吗）、尽调视角（这里有什么核查点）、投委会汇报视角（怎样让委员三十秒看懂）、风险识别视角（缺口与瑕疵在哪）、客观公允视角（这句话有依据吗）。每写一段用五问过一遍。
- **表格承载事实，正文只存在四类合法句子。** 数据密集的信息（工商、股东、专利、客户、财务）一律进表；正文逐句必须属于四类之一：引导句（表前一句）、事实句（带口径的白描）、识别句（这是谁、什么性质、谁控制谁受益）、判断+核查句（成对出现，判断不落单）。抒情、展望、评价性形容词不是"不建议用"，而是在语法层面就不合法；成段的判断只允许出现在股东结构分析段、财务趋势分析段、存在问题节与综合判断节。详见 `references/writing-craft.md` 第二节。
- **事实 + 分析双拍收尾。** 关键模块（股权、团队、财务、客户集中度）表后必须有分析句，落到"整体来看……""后续仍需重点关注……"；纯罗列不加判断是失职，无依据拔高是失格。
- **瑕疵如实记录，不回避不渲染。** 0元/低价股权转让、代持、认缴未实缴、社保参保数与员工数差异、子公司设立的真实用途、持续亏损、毛利率波动，照实写入表格与正文，配一句审慎归因与核查指向。这正是资深投资人的可信度来源。
- **绝不出现机械来源句与宣传语。** 不写"根据某某材料显示""从文件中可以看出"；改为"在股权结构方面……""截至××年××月……"。例外：财务数据、访谈信息、公司自报预测必须交代口径，用具体溯源句（"根据公司提供的2024年度审计报告""据访谈""公司根据在手订单情况预测"），详见 `references/writing-craft.md` 第四节。禁用"行业领先""前景无限""风险很小"等一切无法证明的表达。
- **一切有据，缺则查，查不到则标注。** 资料包 > 联网权威来源 > "相关资料尚未提供／该事项仍需进一步核查"。三档之外不得凭空生成股东、比例、金额、日期、专利、客户或合规结论。资料与公开信息冲突时并列两个口径，提示"需进一步核实"。
- **守住章节边界。** 公司情况只放核心财务数据快照、问题提示与公司自报预测；深度财务分析（明细科目、比率体系、审计调整）归财务分析章节。产品技术细节、商业模式归主营业务分析；市场规模、政策归行业分析。客户供应商在本章只谈集中度与依赖度，收入结构分析归主营业务。

## 参考文件导航

- `references/structure.md`——**起草前必读**。第 0 节公司事实台账字段（含包内多文件冲突的并列处理规则）；第 0.5 节三角验证矩阵（跨模块事实级互锁核验）；正文逐层（基本信息/股权变动/财务数据/合规/上市规划/综合判断）讲清每个标题层级写什么、为什么、配什么表，第六节含红旗组合命中后的综合判断写法；末节结构自适应裁剪规则。
- `references/writing-craft.md`——落笔时读。五重视角的落地方法、四类合法句子的语法约束、段落四拍结构、引出句式库、溯源表述规则、审慎表达与禁用语清单、成稿质检清单（十四项）。
- `references/data-and-tables.md`——涉及数字或表格前读。持股比例/穿透比例/投后估值/稀释/CAGR 等全部公式、口径与单位规则（含包内冲突处理）、数字勾稽自检清单、联网检索与取信规则、标准表模板 T1–T15 字段定义。
- `references/red-flags.md`——**每写完一节扫一遍**。四十年经验的红旗模式库：按文档位置索引的死法清单（现象→为什么危险→核查动作），命中即"白描＋出口"落入正文或风险表；第十二节组合拳命中后须在综合判断节明确点名，不得拆散稀释。
- `references/gold-examples.md`——需要"照着写"时读。两份范例（伊隆纬特=早期、因诺科技=成长期）的标注骨架与高质量段落拆解：团队履历段公式、股东识别段、逐次股权变动写法、财务分析段、存在问题段、上市差距分析段。

## Word 输出

`scripts/build_docx.py` 只负责排版，不负责写作。把公司情况内容组织成 JSON 再运行：

```bash
python scripts/build_docx.py content.json output.docx
```

`content.json` 结构（只交付本章节时 blocks 直接从 `四、公司情况` 起，`toc` 设 false；骨架样例见 `assets/content_skeleton.json`）：

```json
{
  "cover": {"title_lines": ["关于投资XX公司的", "立项报告（公司情况）"], "org": "XX投资管理有限公司", "date": "2026年7月"},
  "toc": false,
  "blocks": [
    {"type": "h1", "text": "四、公司情况"},
    {"type": "h2", "text": "（一）基本信息"},
    {"type": "h3", "text": "1.工商信息"},
    {"type": "table", "header": ["项目", "内容"], "rows": [["企业名称", "……"]]},
    {"type": "p", "text": "在公司基本情况方面，……"},
    {"type": "note", "text": "【待核查：历次股权转让价格及对应完税凭证尚未提供】"}
  ]
}
```

块类型：`h1/h2/h3/h4`（标题，编号自带）、`p`（段落，`"bold":true` 用于综合判断金句）、`bullet`（荣誉资质列表）、`table`（`header`+`rows`，宽表给 `widths`）、`note`（灰色待补提示）、`pagebreak`。表格默认仿宋_GB2312 10.5pt、表头浅蓝底，正文公文格式（仿宋三号、首行缩进、固定行距 28 磅）。

## 勾稽机械校验

`scripts/reconcile_check.py` 只做算术核验，不做措辞或逻辑判断，是第 7 步"成稿自检"的辅助工具而非替代：

```bash
python scripts/reconcile_check.py content.json
```

自动识别股东结构表、人员专业结构表、客户/供应商表、核心财务表等标准表格并核验：持股/股权比例求和=100%、认缴与实缴出资合计与工商信息表交叉一致、人员分项之和=总数、客户供应商明细之和=合计行、资产=负债+所有者权益、毛利率反算与表列一致等（对应 `data-and-tables.md` 第三节勾稽自检清单）。数据为空或缺表时相应检查项标记"跳过"而非"通过"，不会把骨架占位误判为核验通过；发现 FAIL 项要回到原始资料核实数字本身，不得反向调整数字让脚本通过。脚本无法替代 `red-flags.md` 的人工扫描与三角验证矩阵——它只保证"表格算得对"，不保证"事实立得住"。

## 读取 .docx 资料包

```bash
python scripts/extract_docx.py "某公司-尽调资料.docx" out.txt
```

逐块输出段落（含样式名）与表格（标 rows/cols），便于建台账。Windows 上若默认 python 缺 docx 库，用装有 python-docx 的解释器运行。PDF、Excel 资料用对应技能（pdf / xlsx）读取后同样登记进台账。
