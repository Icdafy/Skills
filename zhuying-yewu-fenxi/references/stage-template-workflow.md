# 阶段选择、固定标题与资料填空

## 先取得用户的阶段答案

调用本技能撰写、续写、修订或复核章节时，第一步核对当前项目是否已有用户明确给出的阶段答案。未给出时，先问：

> 这次项目采用哪套模板：早前期（伊隆纬特）还是中后期（因诺科技）？

等待用户回答后才选模板、起草或改稿。不得依据融资轮次、收入规模、业务板块数量、文件名称或模型判断代替用户回答。同一项目本轮连续调用三个技能时，共用用户已明确选定的阶段，不重复询问；换项目或答案不明时重新问。用户在调用语句中明确指定阶段，即视为已回答。纯安装、迁移、故障排查及格式修复不要求重新选写作模板。

| 用户答案 | 唯一标题来源 | 逐项原文对照 |
| --- | --- | --- |
| 早前期／早期／伊隆纬特模板 | `assets/templates/early.json` | [早前期原文对照](template-early.md) |
| 中后期／因诺科技模板 | `assets/templates/mid-late.json` | [中后期原文对照](template-mid-late.md) |

每个技能只加载本技能选定阶段的模板。三个技能必须使用同一项目阶段，不能行业选一套、主营或公司情况另选一套。

## 固定部分与填空部分

JSON的 `source_headings` 保存全部原文标题及位置；`nodes` 是实际写作模板。两者通过 `sources` 一一对应。仅对编号后的排版空格作归一，不擅自润色原文通用标题。

- 普通标题文字、层级和顺序固定。不得自行增加、删除、合并、重排标题，不得回到旧版通用骨架或让逻辑复核改题。
- `{变量}` 仅替换案例特有的产品、板块、人名、日期、客户结构、技术结论及上市市场，填写依据来自当前公司资料和必要的公开核验。保留标题的分析用途，禁止借变量插入无关章节。
- `repeat` 只用于模板明确标记的团队成员、股东、历史沿革事项及财务问题，按当前项目实际数量展开并自动顺序编号。完整覆盖资料中的相应对象；数量变化不构成新增分析模块。源案例的人员、股东、事项数量不是新公司的事实。
- 原报告“持续亏损”“央企主导”等判断只用于说明槽位用途，不能预设新公司也有该情况。技术优势标题必须与正文证据一致，不得为填满格子编造优势。
- 除上述重复组外，业务板块、产品线及技术子项的槽位数量保留原模板。如果新公司不适用某个槽位，先说明具体不适配位置并请用户明确调整该项目模板；不可自动切换阶段、复制业务凑数或静默删节。
- 资料缺失时继续整理可写部分，在正文外列出对应标题的缺口；不把空标题、占位正文或无依据结论作为完整成稿交付。已核实某事项不存在，可以在相应标题下陈述核查范围与客观结果。未提供材料不能写成“不存在”。

原章号保留：早前期为二、三、四章；中后期行业为第三章、主营为第四章，公司情况分为第二章“公司情况介绍”和第五章“拟投资主体相关情况”。这是原文件真实安排，中后期不套用旧版“基本信息—股权变动—财务数据”骨架，也不默认并入独立的第六章财务分析。整报告合并时按用户指定目录统一章号；这属于明确的项目级改动，记录映射后再校验，不能假称与原版标题完全一致。

## 逐标题填入当前公司事实

先通读资料包与访谈，建立“模板节点 → 需要回答的问题 → 事实和数字 → 来源及期间 → 正文位置”的映射底稿。原报告只提供结构和写法，不提供新项目事实。

行业分析：资料包用于识别产品、客户场景和产业链位置；行业规模、政策、竞争与产业链事实用权威公开资料核验。主营业务：结合产品资料、订单、合同、技术测试和访谈说明客户价值、实现机制、竞对差异与壁垒。公司情况：以工商、股权、团队、权属、审计及相关资料填入对应节点，口头解释与书面事实分清。

不要把整份资料机械塞进标题。每节直接回答该标题的问题，说明与投资选择的关系。论证不足时补证据、解释和段落衔接；标题仍按模板固定。正文遵守中性公文风格和既定禁用套话规则。

## 可执行流程

以下命令从技能根目录运行；路径含空格时加引号。`--stage` 必填，值由用户答案映射为 `early` 或 `mid-late`。

```bash
# 1. 获得用户答案后生成工作骨架；这是待填文件，不能直接交付
python scripts/stage_template.py init --stage early --output "任务目录/draft.json"

# 2. 从 draft.json 的 report_template.bindings 提取字段，按资料填写 bindings.json
#    重复项写成对象数组；其他槽位填文字。用实际字段重新生成固定标题，再撰写正文
python scripts/stage_template.py init --stage early --bindings "任务目录/bindings.json" --output "任务目录/content.json"

# 3. 完成正文后核对标题、顺序、空节与占位项；Markdown交付也执行此检查
python scripts/stage_template.py check "任务目录/content.json"
python scripts/style_check.py "任务目录/content.json"

# 4. 需要Word时生成；渲染器也会检查带 report_template 的内容
python scripts/build_docx.py "任务目录/content.json" "任务目录/report.docx"
```

每次只在首次填入正文前执行 `init`，它会写入指定输出文件；正文写成后不要用 `init` 覆盖已有成稿。调整绑定值时在新的工作文件生成标题并逐项迁移正文。

新写章节必须保留 `report_template` 元数据并通过 `check`。无Python执行条件的Agent，读取同一JSON和原文对照表逐标题人工核对，说明未运行机械检查；仍须先取得用户阶段选择。不得以宿主不支持脚本为由自动选模板。

脚本核对标题一致性和填空状态，不验证事实真伪或投资逻辑。交付前仍需执行 [投资逻辑复核](investment-logic-review.md)，确认必要性、技术机制、比较基准、壁垒和客户价值讲清楚；复核只能修改正文及有证据的变量值。用户明确改动固定结构时，记录其指令和差异，按已授权项目模板逐项核对，不能删除元数据冒充原模板检查通过。
